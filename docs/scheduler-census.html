The split was chosen for trigger precision — GCP for market-clock-anchored jobs, Modal for anything GHA's minutes-of-jitter or 6-hour ceiling can't hold. In practice cron is actually firing on two of the three hosts: GitHub Actions (10 workflows) and Modal (its one deployed app, free-model-refresh, weekly); GCP Cloud Scheduler has never been provisioned — its setup script has not been run against the project. And independent of any of that: all three of GCP's designed targets, and four of GitHub Actions's, point at routes that don't exist yet.

What the split actually costs

Two consequences of running the same job's design on more than one host, plus the pattern the route-status page already found repeating here.

RUNNING TWICE

Free-model refresh fires on both GHA and Modal, every Monday

benign, wasteful

GitHub Actions at 06:17 UTC, Modal at 09:00 UTC — same probe, same target file. Both are idempotent, so whichever runs second finds nothing changed and no-ops. The real cost is two full probe passes against the OpenRouter catalog, and a small chance of two PRs in the same week if a model flaps between the two runs.

Not urgent. Worth consolidating onto one host when it's convenient.

WOULD RUN TWICE

Precompute-AI is one modal deploy from double-spending its own quota

not yet live — still a live landmine

GitHub Actions runs precompute-ai.yml daily at 00:10 UTC hitting POST /api/pipeline/precompute-ai. Modal's nuwrrrld-precompute-ai app is scheduled for the identical 10 0 * * * against the identical route — it's only inert because it has never been deployed. Deploying it without first disabling the GHA twin means two schedulers hitting the same endpoint in the same minute, doubling the spend of the exact free-tier AI quota the job exists to protect, for identical output.

Rule already written down: before modal deploy of any portal app, disable its GHA twin's schedule: block first (keep workflow_dispatch), and say so in the commit.

SAME BUG, DIFFERENT HOST

GCP's precision doesn't help when the target route doesn't exist

confirmed against the repo

All 3 designed GCP jobs point at routes that are absent from the codebase — not just unimplemented handlers, genuinely no file: /api/pipeline/signals-refresh (also the route GitHub Actions' afternoon-pipeline already 404s on — see below), /api/briefing/run, and /api/verdicts/score. Provisioning the scheduler would fix nothing; the jitter GCP exists to avoid was never the blocker.
