Context, and the Rules Built Around It

A context window fills up as a session runs, and what it loses first is the most valuable thing in it. These are the six always-on rules that respond to that — and the one thing none of them can do.

What context actually is

Every message, file read, and tool result in a session accumulates into one finite window. When it fills, the oldest material gets summarized away to make room — the session keeps working, but it is now reasoning from a compressed retelling rather than the original.

What degrades, in order. This is the part that makes the timing rules matter — loss is not uniform, and the most useful content goes first.

Exact strings go earliest: the literal error message, the failing line number, the command that reproduced it. Then negative knowledge — why something wasn't done, the approach tried and abandoned, the finding checked and dismissed as a false positive. To a summarizer that looks like noise, so it is discarded wholesale. Then causal ordering flattens: which fix caused which failure collapses into an undifferentiated list of events.

The tier ladder

Six bands, assessed at the top of each turn. The badge is prepended to the response so pressure is visible without being asked about. Only two tiers carry a required action.

0–20% TIER 1 · CLEAR No badge shown. Full working memory.
20–40% TIER 2 · LIGHT Optional note if many files have been read.
40–60% TIER 3 · MODERATE Action: offer the session handoff, once. The detail worth capturing is still intact here. This is the newest rule and the one that changes behavior most.
60–75% TIER 4 · HEAVY Recommend a new session or /compact. Don't re-offer the handoff here if it was already declined.
75–90% TIER 5 · CRITICAL Action: name the specific next step. Re-raise the handoff as a recommendation, not a question.
90–100% TIER 6 · MAXIMUM Summarization already active — earlier detail may be gone. Note branch/stash state before clearing.

Why halfway, and not at the end

The instinct is to write a wrap-up when the work is finished. That is the worst available moment, and the reasoning is worth spelling out because “50%” is otherwise an arbitrary number.

  1. Exact strings vanish firstBy Tier 5 you are describing an error message from memory of a summary of it, not from the message.
  2. Negative knowledge vanishes entirelyThe highest-value content in any handoff — what was ruled out and why — is the first thing discarded, because it reads as noise.
  3. Causal ordering flattensWhich fix caused which failure becomes an unordered list of things that happened.

The four layers

Two rules, one skill, one hook. They are separate because they have genuinely different capabilities — in particular, only two of the four can see context at all.

The constraint that forced this shape. Hook payloads carry no token or context-window data — only session_id, transcript_path, cwd, and a termination matcher. Verified against Claude Code's hook documentation, not assumed.

So a hook cannot gate on “context above 50%.” That judgment exists only inside the model's own assessment, which is why the trigger had to be a rule and could not be a script. The hook is demoted to what it can actually do: notice after the fact that a session ended without a handoff, and leave a breadcrumb.

All six rules

Everything in ~/.claude/rules/, auto-loaded into every session regardless of project. Two are about context; the rest encode lessons from specific incidents.

Handoff at Half Context handoff-at-half-context.md

Offer a session handoff once at Tier 3, then act on the answer and drop it. Includes explicit do-nots, because the failure mode here is nagging: don't re-offer within a tier, don't write it unprompted (it costs the very resource in question), don't interrupt mid-unit, and don't substitute an inline chat summary for the durable file.

TIER 3 · ONCE

Context Bloat Warning context-bloat-warning.md

The six-tier ladder above. Prepends a one-line badge before the first sentence of a response — never at the end, where it would be read after the reader has already decided what to do next.

EVERY TURN

Artifact and Local HTML artifact-and-local-html.md

Any standalone HTML deliverable produces both a committed local file and a published artifact. Each covers the other's gap: the file is diffable and offline, the artifact is shareable and previewable. Producing one repeatedly forced a follow-up request for the other.

ON HTML DELIVERABLE

Stay on Branch After Merge stay-on-branch-after-merge.md

Never git checkout main into a tree holding newer work. Written after work vanished twice: a squash-merge of an older branch, then a checkout of main, silently reverted newer on-disk edits. To advance the ref without checking it out: git fetch origin main:main.

AFTER gh pr merge

Mobile ↔ Web Wiki Sync mobile-web-wiki-sync.md

A PR in either surface refreshes the cross-surface parity pages in both wikis, in the same task. Enforced by a hook that doesn't just remind but verifies — because the real failure was wiki content written, left uncommitted, and never included in the PR it documented. A reminder can't catch that; a git status check can.

ON gh pr create / merge

Mamba Package Manager mamba-rules.md

Mamba over conda for every environment operation, with conda config as the sole exception. Install all packages in one command; never run pip outside an activated environment.

Two stops, not one

The easiest thing to confuse: there are two different ways a long session can end, and they need opposite handling.

/resume-safeend-session
Trigger Context nearly exhausted, mid-run Deliberate stop, context still healthy
Intent Keep this run alive across a context wall Close the run down on purpose
Output Checkpoint + scheduled wakeup to auto-resume Committed handoff for a fresh session

Use one or the other for a given stop — never both.
