Six Crons, One Deployed

The Modal apps in this stack carry modal.Cron(...) lines that read like running schedules. Five of the six are not running at all — and two of the three that overlap a GitHub Actions workflow are set to fire at the same minute.

The issues

ordered by what it costs you

Two schedulers, one free-tier bucket, the same minute

deploy/precompute-ai/modal_app.py  ·  .github/workflows/precompute-ai.yml

fires on deploy

Both the Modal app and the GitHub Actions workflow are scheduled at 10 0 * * *, and both do the same single thing: POST /api/pipeline/precompute-ai. The timing is not incidental — 00:10 UTC is ten minutes after OpenRouter's free tier resets, chosen because that is when the day's allowance is freshest.

Modal deploy/precompute-ai/modal_app.py schedule=modal.Cron("10 0 * * *") GHA .github/workflows/precompute-ai.yml cron: '10 0 * * *' both → POST /api/pipeline/precompute-ai (maxSubjects: 10)

The job exists to protect the interactive AI allowance from batch work. Running it on both platforms doubles the spend of exactly the quota it was built to defend, for output that is byte-identical. The workflow's own header says to run one of them; nothing enforces it.

Why it hasn't bitten yet: the Modal app has never been deployed, so only the workflow fires. The damage happens the moment someone runs modal deploy on it — with no error, no warning, and a symptom (afternoon chat requests hitting a spent quota) that looks nothing like its cause.

Fix

Pick one platform per job. Before any modal deploy of a portal app, comment out the twin workflow's schedule: block — keep workflow_dispatch so the manual path survives.

The free-model refresh is already double-firing every Monday

deploy/free-model-refresh/modal_app.py  ·  .github/workflows/refresh-free-models.yml

live now

This is the same duplication as above, except it is not hypothetical — it is happening weekly. GitHub Actions probes the OpenRouter catalog at 06:17 UTC; Modal probes it again at 09:00 UTC.

$ modal secret list free-model-refresh created 2026-07-14 18:11 EDT last used 2026-08-31 05:00 EDT └─ = 09:00 UTC, a Monday exactly modal.Cron("0 9 * * 1")

The secret's last-read timestamp is the proof: the deployed Modal cron is firing on schedule. Mostly this is benign — both runs are idempotent, and whichever lands second finds nothing changed and no-ops. The real costs are two full catalog probe passes a week, and a duplicate PR any week a model flaps between 06:17 and 09:00.

Fix

Retire one schedule. Modal is the better keep here — it already holds the GH_TOKEN and bakes the runner script into its image rather than curling it from main at run time.

A cron in the source is not a cron that runs

5 of 6 apps  ·  2 secrets referenced but absent

structural

Reading the repo, six apps look scheduled. In the workspace, one exists. modal.Cron(...) is inert until modal deploy registers it, and nothing in the source distinguishes a live schedule from a dormant one.

$ modal app list --json [{ "description": "free-model-refresh", "state": "deployed", "tasks": "0" }] $ modal secret list nuwrrrld-secrets last used 2026-08-12 ← homebase apps: not deployed free-model-refresh last used 2026-08-31 ← firing referenced by source, absent from the workspace: nuwrrrld-hydration ← deploy/universe-hydration/modal_app.py nuwrrrld-precompute ← deploy/precompute-ai/modal_app.py

The two missing secrets have a sharp edge worth knowing: modal.Secret.from_name() resolves while the app is being constructed, so a deploy without the secret fails at deploy time, not on the first run. That is the good version of this failure. The bad version is the quiet one — five dormant apps that a reader, or a future session, will reasonably assume are covering work that nothing is covering.

  • nuwrrrld-universe-hydration — dormant; GHA covers it at 22:30 UTC
  • nuwrrrld-precompute-ai — dormant; GHA covers it at 00:10 UTC
  • nuwrrrld-signals — dormant; nothing else covers it
  • nuwrrrld-drain — dormant; nothing else covers it
  • nuwrrrld-finnhub-ws — dormant; no schedule by design, manual only
Fix

Decide per app: deploy it, or say in the file's docstring that it is a source-only alternative and name what covers the work instead. Either is fine; the ambiguity is not.

A schedule that silently moves an hour in November

homebase/modal_locrun.py

latent

The signal pipeline is scheduled 15 18 * * 1-5 with the comment “2:15 PM ET weekdays”. That is true during EDT only. Modal crons are UTC with no timezone support, so when the US falls back the same expression becomes 13:15 ET — the job moves an hour earlier into the trading day without a single line changing.

modal_locrun.py modal.Cron("15 18 * * 1-5") EDT (Mar–Nov) → 14:15 ET ✓ intended EST (Nov–Mar) → 13:15 ET ✗ silent one-hour drift

The GitHub Actions afternoon pipeline already solves this: it registers both 15 20 * * 1-5 and 15 19 * * 1-5 and gates the real work behind a market-hours check inside the job. The Modal file has neither half of that pattern.

Fix

Harmless while the app stays dormant. If it is ever deployed, port the two-cron-plus-gate pattern first — a schedule that is correct for eight months a year is the kind of bug that gets found in January.

What to do, in order

  1. Retire one of the two weekly refresh schedules

    The only issue costing anything today. Comment out the schedule: block in refresh-free-models.yml, keep workflow_dispatch.

  2. Write the deploy rule down where it will be read

    Never modal deploy a portal app without first disabling its GHA twin's schedule. Both files' headers say “run one of them” — put it in the commit message too.

  3. Resolve each dormant app explicitly

    Deploy it, or mark it source-only and name its substitute. Start with nuwrrrld-signals and nuwrrrld-drain, which have no substitute at all.

    modal app list --json # the only honest source of truth

  4. Fix the DST drift before deploying the signal pipeline

    Two cron expressions plus an in-job market-hours gate, matching what afternoon-pipeline.yml already does.
