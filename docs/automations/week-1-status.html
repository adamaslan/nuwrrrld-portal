What planning actually settled

These are decisions, not code. They redirected the week away from the roadmap's original plan and are the durable output so far.

Modal stays and gets deployed

Decided

The roadmap said delete the Modal precompute schedule. Reversed: all three apps stay fully functional and get deployed, so they can be tested and measured.

Run both schedulers, don't pick a winner

Decided

Rather than choosing GitHub Actions or Modal, run both on staggered times and measure which produces more and costs less. Turns a stalled either/or into an experiment.

Spread runs across the day

Decided

Maximize data collection through temporal coverage — with the honest caveat recorded below about what repeated runs can and cannot add.

Test the automations, don't guard them

Decided

A defensive route guard was rejected in favour of a test harness: a static contract suite, a dry-run checker, and a visual report.

The chain repairs itself

Decided

When the checker finds the model chain broken it re-runs the refresh and reports the outcome, instead of only flagging it.

The script picks the models, never a human

Decided

Model ids are chosen by live probing whatever is free that week — no hand-edited list.

The one real risk in running both

precompute-ai fires from GitHub Actions and Modal at 00:10 UTC — the same minute, the same endpoint. Both spend from a single shared OpenRouter free-tier bucket that resets at midnight. The plan moves the Modal copy to 00:40 so the second run measures what the first left behind instead of racing it. Until that edit lands, deploying the Modal precompute app would make a latent double-spend real.

More runs will not produce more bars

A daily price bar finalizes once per session. Running the hydration lane six times a day re-fetches the same bar, and the replacement rule correctly refuses to overwrite it — costing vendor calls for no new history. Extra runs add real data only by pulling intraday timeframes, or by snapshotting how the ranking moves during the day. Both are follow-ups, and neither is assumed silently.

The model chain problem, unchanged

The fallback chain looks four deep and is one deep against the failure that actually happens.

PositionModelVendor
1nemotron-3-ultra-550b-a55b:freenvidia
2nemotron-3-super-120b-a12b:freenvidia
3nemotron-3-nano-30b-a3b:freenvidia
4nemotron-3-nano-omni-30b-a3b-reasoning:freenvidia

All four entries come from one vendor, so an account-level failure takes out the entire chain at once — and an account-level failure is the one that actually occurs. The refresh script ranks candidates by preference and size with no vendor constraint, which is how a single vendor swept every slot. The fix is a per-vendor cap in the selection step, leaving the model choices themselves to the weekly live probe.
