Three decisions worth keeping

The ledger outlives the erasure it records

privacy_requests is deliberately absent from the delete cascade. The record that someone asked to be erased on a given date has to survive that erasure, or the compliance artifact destroys itself. It holds nothing personal beyond the account ID, so keeping it is not in tension with the deletion.

A build that passed while being broken

The timing-safe compare first used node:crypto, which the Edge middleware bundle cannot load. next build printed an Ecmascript error and exited zero. It was rewritten as a pure-JavaScript constant-time loop. Anyone reaching for a crypto import in middleware-reachable code will hit this again.

The consent gate lives on the server

The attribution endpoint returns 204 and stores nothing unless analytics consent is granted. A client-side-only check would be both bypassable and unauditable, so the decision is made where it can be enforced.

The finding underneath the parity number

One account, two different sets of rights

Parity moved from 63% to 62%, which undersells what changed. The web portal now serves GDPR access, erasure and rectification, and blocks tracking until a visitor opts in. The mobile app does neither — against the same Clerk identity.

So a person can exercise their data rights on the website and has no mechanism in the app, and is tracked there without the gate the website enforces. That is two compliance asymmetries on one shared account, and it is a product problem rather than a code-sharing one.

The cheapest correct fix is for mobile to adopt the shared consent module and link out to the portal’s endpoints, keeping the erasure cascade and the ledger single-copy. Both wikis now carry this as the top open item.

Still open

  • Clerk Production instance — dashboard access and DNS. The only item that is purely someone pressing buttons.
  • An analytics vendor, once a data-processing agreement is signed. The sink is built and waiting for one function body.
  • Retention enforcement. Until a job actually deletes on schedule, the published policy would be promising something that doesn’t happen.
  • Restriction of processing — promised in section 8 of the policy, still the one right with no mechanism behind it.
  • The model-provider question. Prompt text reaches third-party inference providers. Nobody has confirmed zero-retention terms in writing, and the model chain changes on its own.
