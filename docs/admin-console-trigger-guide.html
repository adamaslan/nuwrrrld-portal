Firing pipelines from nulogdash

The /dashboard/nulogdash console can now trigger the three model-spending pipelines from the browser. This is the console's only write path — here is how it works, and the security reasoning that shapes every part of it.

branch feat/pipeline-local-runs-fixes scope admin-console-todo.md §1–§5 date 2026-09-08

00What this is

Until this change, everything under app/dashboard/nulogdash/** was a read-only server component. Nothing in a browser session could spend OpenRouter quota or write a database row.

Adding a "run" button is the one change that removes that property, so it was built to a single rule:

The invariant

The browser must never be able to do something scripts/local-trigger.mjs would have refused. The CLI defaults to dry_run: true and refuses --no-dry-run without --yes. The dashboard needs a server-enforced equivalent for both halves, and cannot trust the client for either.

Two Clerk gates already existed for this and were finally wired up: isNulogdashAdmin (verified primary email on an allowlist) guards reading a report; canPerformAdminAction adds a two-factor-enabled requirement and guards anything that mutates. The trigger UI renders only under the second.

01Two ways to trigger

Same routes, same auth secrets, same dry-run contract — different front door.

Live run --no-dry-run --yes Second server call with a one-time token + typed pipeline name

Rate limit None (a human at a terminal) 1 live run / pipeline / 5 min, keyed on user

The pipeline → route → secret map is single-sourced in lib/nulogdash-trigger.ts and mirrors the CLI: followed-tickers and followed-tickers-judge authenticate with CRON_SECRET; precompute-ai with PORTAL_PUSH_SECRET.

02How a live run happens

A genuine sequence — each step is a separate server round trip, and the chain breaks closed at every point.

  1. Admin clicks “Dry run”.

    triggerPipelineRun({ pipeline }) re-derives identity from the session (auth() → currentUser() → canPerformAdminAction), validates the pipeline name against a fixed set, then loopback-POSTs the route with dry_run: true and the bearer secret attached server-side.

  2. Server mints a confirm token.

    On a successful dry run, a single-use token with a 2-minute TTL, keyed to {pipeline, userId}, is returned to the client. It is the browser's equivalent of the CLI's --yes.

  3. Admin types the pipeline name and clicks “Run live”.

    The client sends the token plus the typed string. The “Run live” button stays disabled until the typed text exactly matches.

  4. Server re-checks everything.

    confirmLivePipelineRun re-runs the admin/MFA check, burns the token (valid only if unexpired and an exact match), confirms typedName === pipeline, then calls assertNotProductionDb() and the per-user rateLimit(). Any failure returns an error and fires nothing.

  5. Live POST.

    Only now does the route get dry_run: false, with session: "nulogdash:<email>" so the resulting pipeline_run_log row names who fired it. The pipelines table revalidates.

03Security risks & containment

Every risk this feature introduces, and where in the code it is held. “Contained” means enforced server-side and tested; “needs a human” means the control exists but is inert until someone sets a value.

A browser session spends model quota

contained

Any live run calls OpenRouter and can burn the free-model budget or a paid key.

Held by: MFA-gated visibility; a two-call token handshake (no one-shot live fire); a 1-per-5-min per-user rate limit on live runs; dry run is always the default.

A live run writes production data

needs a human

DATABASE_URL is one string; nothing structurally distinguished a dev Neon branch from production.

Held by: assertNotProductionDb() refuses a live run when DATABASE_URL resolves to PRODUCTION_DB_HOST. Inert until that env var is set in .env.local and Vercel — the guard only warns otherwise.

The auth secret leaks to the client

contained

The pipeline routes authenticate with Bearer CRON_SECRET / PORTAL_PUSH_SECRET. If the browser called them directly, that secret would have to ship to the browser.

Held by: the mutation is a Server Action, not a client fetch. The secret is read from process.env and attached to a loopback request entirely server-side; the client payload is { pipeline } and, for the second call, { pipeline, confirmToken, typedName } — nothing else.

Cross-site request forgery on a spend endpoint

contained

A hand-rolled POST route that spends money is a CSRF target.

Held by: Next.js Server Actions carry a built-in same-origin check. No new public mutation endpoint was added.

Client forges identity or permission

contained

A payload claiming “I am an admin” or “this is authorized”.

Held by: both actions re-derive userId and re-run canPerformAdminAction from the Clerk session on every call. Nothing the client says about identity is read. The pipeline string is validated against a closed union — an unvalidated value there would be a request-forgery primitive aimed at the app's own internals.

Replay / double-fire

contained

Re-submitting a confirmation, or a double-click storm.

Held by: the confirm token is deleted on first use regardless of outcome and expires after 2 minutes; the rate limiter blocks the immediate retry. Caveat: both stores are in-process (per the lib/rate-limit.ts note) — best-effort on serverless, enough to force deliberate use, not a distributed lock.

The auth boundary moved (proxy.ts rename)

contained

middleware.ts → proxy.ts touches the file that decides who is authenticated, and shifts it from the Edge to the Node.js runtime.

Held by: behaviour is unchanged — clerkMiddleware() stays the default export (valid under the proxy convention), config.matcher is untouched. Re-verified locally: unauthed /dashboard/nulogdash still 307s, internal-secret routes still reach their bearer check (401, not an edge 404), /api/council/public still bypasses auth.protect(). The pure-JS timing-safe compare in lib/http-auth.ts is kept as-is.

MFA banner over-promised

contained

MfaNotice named actions that don't exist (“impersonate, disable, reset password, reindex”).

Held by: copy narrowed to what actually exists — “actions that spend model quota or write rows (triggering a pipeline run)” — with the test updated to assert it.

Widening what the buttons can fire

deferred

Adding followed-tickers-select / hydrate-universe to the console also widens the trigger surface.

Decision: deferred, not declined — a deliberate follow-up after the trigger UI has proven safe, not folded into this change.

  • .env.example — documented, no value.
  • __tests__/pipeline-db-guard.test.ts — new, 6 cases.

  • app/dashboard/nulogdash/pipelines/page.tsx — ?limit= pagination (50 default) into the already-clamped listPipelineRuns, with a 50·100·200 row.

05Still needs a human

The code is in; these cannot be done from a diff. Tracked in docs/manual-setup-todo.md §9.

  • Confirm the local DATABASE_URL is a dev Neon branch, not production.
  • Set PRODUCTION_DB_HOST (host only) in .env.local and the Vercel project env. Until then the prod-DB guard only warns.
  • Enrol Clerk MFA on the admin account — the trigger buttons render only under canPerformAdminAction, which requires it.
  • Run one real end-to-end trigger as an MFA admin: dry run → row appears attributed to your email; live run → typed confirm required, second attempt rate-limited; with PRODUCTION_DB_HOST matching the local host, the live run is refused.
  • Decide later whether followed-tickers-select / hydrate-universe should ever be triggerable (deferred).
