Root cause (now fixed) — the OpenRouter API key was expired

At the start of this run, a direct probe of GET https://openrouter.ai/api/v1/auth/key with the key from .env.local returned 401 {"error":{"message":"API key expired."}}. Every model call — seat calls, streaming calls, the precompute batch — failed the same way and walked its entire fallback chain to get there. Catalog probes (/api/v1/models) still passed, so the FREE_MODEL_CHAIN ids were healthy; the credential was the single broken link. Resolved the same day by rotating OPENROUTER_API_KEY (still to do: the same rotation in the Vercel project env). The observability findings in §2–§5 stand regardless — they are about how the pipeline reported the outage.

§ 01 / 06Credentials & environment

The findings that a new key fixes outright — plus the ones a new key won't.

  1. critical

    The dev/CI OpenRouter key is expired, not just rate-limited

    Both /auth/key and /chat/completions return 401 "API key expired.". This is a hard credential failure that never self-heals — unlike the 402/429 the fallback chain was built for. Until it is rotated, every AI feature in the portal is dark locally.

  2. high

    27 of 35 live tests fail for exactly one reason

    council-verdict (8), streaming (5), openrouter-resilience bursts (3), model-chain and council-verdict format contracts — all throw OpenRouter 401: … all models failed. The suite has no assertion that separates "credential expired" from "model misbehaved", so 27 red lines all read as product regressions.

  3. high

    refresh-free-models.mjs refuses to run without a live key

    The weekly chain-maintenance job exits with OPENROUTER_API_KEY is required (or pass --no-probe). So the moment auth breaks, the script that keeps FREE_MODEL_CHAIN current also stops — the chain silently freezes exactly when it might need updating.

  4. medium

    The live vitest project shares the dev key

    test/live-setup.ts loads .env.local and keys off OPENROUTER_API_KEY.length > 0. There is no dedicated CI probe credential and no owner alerted when it lapses — a prod key rotation takes the whole live suite down with it and nothing pages.

  5. medium

    describeLive can't tell "no key" from "dead key"

    It only checks presence, so an expired key runs every live test to a failing assertion instead of skipping with a single clear "credential expired — suite skipped" line. The setup file's own warning ("a green run in this state proves nothing") never fires here because the run isn't green — it's just misattributed.

§ 02 / 06Error handling & observability

How the pipeline surfaces a total model outage to the humans and cron jobs watching it.

  1. critical

    POST /api/pipeline/precompute-ai returns 200 OK on total failure

    Observed body: {"ok":true,"generated":0,"attempted":2,"quotaExhausted":false, "results":[{…"reason":"OpenRouter 401: all models in chain failed"}×2]}. The Modal function checks response.raise_for_status() — a 2xx — and logs a successful run. A nightly job that produced zero artifacts looks identical to one that worked.

  2. high

    quotaExhausted: false on an auth failure is actively misleading

    The Modal app has a dedicated warning path for quotaExhausted ("something is spending it before the nightly run"). Because a 401 doesn't set that flag, the one alarm the pipeline has for "AI batch produced nothing" stays silent for the failure that actually happened.

  3. high

    Every model failure collapses to one opaque string

    fetchWithModelFallback throws `OpenRouter ${lastStatus}: all models in chain failed` — the status is interpolated into prose, not returned as a field. Downstream callers can't branch on 401 vs 402 vs 5xx without string-matching an error message.

  4. high

    Council routes map a permanent auth error to a transient-sounding 503

    /api/council/sample → 503 "Council unavailable"; /api/council/public → 503 "Council demo temporarily unavailable". "Temporarily" is wrong — an expired key is permanent until someone acts. The stack is logged at error level with no auth-vs-outage tag for alerting.

  5. medium

    No circuit breaker across a burst

    The resilience test fires a 5-seat parallel burst; each seat independently walks primary + 4-chain and independently discovers the same dead key — up to 11 round trips per deliberation, every one predestined to 401. Nothing caches "this key is bad right now."

  6. medium

    Failure messages misname the failure

    "has at least one model fast enough for an interactive JIT call" fails with no model answered at all; the burst test fails with every seat failed under a 5-way parallel burst. Both read as latency/concurrency findings; both are auth. A test that can't name its own failure cause sends the next engineer down the wrong path.

§ 03 / 06Test-suite design

What the split between a green mocked suite and a red live suite tells us about coverage.

  1. high

    npm test is green while the models are unreachable

    The default script runs only unit + components (51/51 here). The live project is opt-in. CI green therefore carries no signal about whether OpenRouter actually answers — the two suites disagreed completely this run and nothing flagged it.

  2. high

    Format-contract tests have no offline fixture path

    All 8 council-verdict.live.test.ts cases — "survives stripReasoning", "parses into four fields", "emits a single JSON object JSON.parse accepts" — need a live completion. With the model unreachable they give zero signal about the parser, which is the part most likely to actually regress.

  3. medium

    Stream-reconstruction logic goes dark when auth is down

    "does not drop or duplicate the primed bytes when reconstructing the stream" is a genuinely valuable regression guard for fetchWithModelFallbackChecked. It has no mocked twin, so the byte-replay path in the streaming variant is untested whenever OpenRouter is unavailable.

  4. medium

    The latency SLO test can't fail for a latency reason here

    expect(healthy[0].latencyMs).toBeLessThan(BUDGET) is never reached — the guard expect(healthy.length).toBeGreaterThan(0) throws first. The interactive-JIT latency budget is currently unverifiable, and will stay that way silently once a key is restored if the ordering isn't revisited.

  5. medium

    Catalog checks pass, seat-behaviour checks fail — and nothing correlates them

    "every FREE_MODEL_CHAIN id is present" and "priced at $0" are green; every call using those ids is red. A human reads the whole log to conclude "ids fine, key dead." A single pre-flight assertion on /auth/key at suite start would state that in one line.

§ 04 / 06Model chain & seat configuration

Structural notes on the fallback design, several already admitted in code comments.

  1. high

    The fallback chain has "nominal depth 4 and real depth 1" against an account failure

    The comment on FREE_MODEL_CHAIN says it outright. Three of four entries are NVIDIA Nemotron; none of the depth helps when the failure is the shared API key. This run is the exact scenario, and the chain absorbed none of it.

  2. high

    SEAT_MODELS is a hand-maintained literal "with no scheduled maintainer"

    Its own comment records that 5 of 6 seats sat on retired ids as recently as 2026-08-18 and 2026-09-02. The primary-model tier is one missed catalog audit away from silently degrading every seat down to the chain — a degraded seat "looks like a working one from the outside."

  3. medium

    Empty-completion-as-success is patched per-path, not centrally

    fetchWithModelFallbackChecked (the variant that treats a content-free 200 as failure) is opt-in and used only by /api/portfolio/health-ai. /api/nuai and /api/brief still call the unchecked fetchWithModelFallback. The bug class (BUG-4, BUG-5, and the 2026-09-02 max_tokens 500→1200 fix) keeps recurring because the guard isn't the default.

  4. medium

    The per-seat retry ladder can blow the deliberation budget on its own

    runSeat allows a 20s abort per model, up to 5 models (primary + 4 chain) = ~100s worst case per seat, across 5 debate seats. Against a slow-failing provider (not this run's fast 401), the ladder alone can exceed the route's maxDuration = 300.

  5. medium

    All resilience investment targets model rot, not credential rot

    Vendor spread, weekly refresh, catalog probes, retired-id detection — all guard against a model disappearing. The failure that took the whole system down today was the key. There is no equivalent monitoring, alerting, or graceful-degrade path for "the account is unauthenticated."

§ 05 / 06Pipeline & sweep infrastructure

What blocked a fuller end-to-end run of Modal and the other pipelines.

  1. high

    NULOGDASH_BASE_URL= (empty) defeats its own default

    scripts/nulogdash.mjs does process.env.NULOGDASH_BASE_URL ?? "http://localhost:3000". An empty string is not undefined, so ?? keeps it, and every probe failed with dev server unreachable at  — Failed to parse URL from /api/health. Needs || or an explicit trim-and-fallback. The first sweep this run reported 53 false "blocked" before the var was overridden.

  2. high

    Three OpenRouter-consuming pipelines can't run locally at all

    CRON_SECRET is commented out in .env.local, so /api/pipeline/followed-tickers, …/followed-tickers-judge and …/followed-tickers-select all return 503 "CRON_SECRET not configured" — the daily observer, the weekly LLM-as-judge, and the selector are untestable without adding the secret.

  3. high

    The sweep has never exercised the interactive AI paths

    NULOGDASH_SESSION_COOKIE unset → 28 of 59 features blocked, including nuai, council, council-deliberate, brief, holdfold, portfolio-health-ai, signals-digest. Coverage of every user-facing AI feature is gated on a manual Clerk cookie paste that no one refreshes.

  4. medium

    Inventory drift: 21 warnings, and routes that 404 on probe

    The sweep marks /api/analyze, /api/disclaimer, /api/legal-consent, /api/privacy/{delete,export,profile} as fail — HTTP 404. The inventory lists endpoints that no longer resolve; nulogdash:inventory reports "21 drift warning(s)" and several routes with "no FEATURE_META entry."

  5. medium

    Only the zero-model lane actually completed

    POST /api/pipeline/hydrate-universe returned 200 · written:4 · modelCalls:0 in ~0.8s — the no-AI coverage path is healthy. Every path that needs a model (precompute-ai, council/*) failed. "Run the pipelines as fully as possible" currently bottoms out at: the part that doesn't touch OpenRouter works; nothing else does.

§ 06 / 06 · post-rotationWhat the working key exposed

Re-run after OPENROUTER_API_KEY was replaced with a valid credential, same day. These are new, not carried over.

  1. critical

    precompute-ai aborts at 60s — it cannot complete one subject even with a good key

    With auth fixed, POST /api/pipeline/precompute-ai {"maxSubjects":1} ran for 61s and returned 200 · generated:0/1 · reason:"This operation was aborted". The route wraps the model call in a 60_000ms AbortController (route.ts:236); the chain can't produce a usable completion inside it. The nightly Modal job would do this every night and log a 2xx "success" each time.

  2. high

    The two largest chain models are unfit for a latency-bounded call

    Dev-log trace for that run: nemotron-3-ultra-550b:free → status=200 sawContent=false (entire reply in reasoning, zero content), then nemotron-3-super-120b:free → 5253 SSE frames, 5252 empty before the timer fired. A direct probe of the 550b model earlier took 53s for a 16-token reply with finish_reason:"length". These sit at the head of FREE_MODEL_CHAIN and on CHAIR.

  3. high

    runSeat's 20s abort will silently drop CHAIR every time

    CHAIR = nemotron-3-ultra-550b:free, which needs ~50s. Since runSeat aborts each model at 20_000ms, the synthesis seat can never be served by its own primary — it always falls through to the chain, whose first two entries have the same problem. The "spend the best model on the hard job" design (§4) is defeated by the timeout.

  4. medium

    Small seats answer fast but return placeholder-grade content

    GET /api/council/sample → 200 in 1.7s, but T1 (cohere/command-r7b) emitted the prompt's own instruction text as its answer (BECAUSE: [1] says "quote" — an evidence id from RULES …) and T2 (gemma-4-31b:free) returned "no data provided". The grounding contract from council-prompting-small-models.md isn't being followed by the models it was written for.

  5. medium

    /auth/key semantics aren't what the code assumes

    The new key reports is_free_tier:false, limit:5, limit_reset:null, usage:0 — a $5 credit cap, not a request count, and no daily reset field. The precompute route's docstring and the Modal app both reason about "OpenRouter's free tier caps the key at ~50 requests/day, resetting at UTC midnight." That model doesn't match this key, so the quotaExhausted accounting and the 00:10-UTC schedule rationale are both built on an assumption the live API contradicts.

  6. high

    Every seat call that answered still missed the 20s budget

    The re-run's latency assertions failed with real numbers 21.3s · 21.3s · 25.2s · 25.6s · 26.0s · 33.3s against expect(<20000). The seat-latency budget in the test is runSeat's own 20s abort — so this isn't a strict test, it's a direct measurement that the chain cannot serve a seat inside the timeout the code will enforce on it in production. CHAIR's test ran 337s; one test hit the 120s vitest ceiling outright.

  7. medium

    The live suite has no tolerance for a transient network blip

    7 of the 19 failures were TypeError: fetch failed / getaddrinfo ENOTFOUND openrouter.ai — intermittent DNS failures during the 18-minute run, while other calls in the same run succeeded. runSeat re-throws any non-abort error instead of advancing the chain (unlike fetchWithModelFallback, which does continue past a network error), so a single DNS hiccup on a seat call = a red test and, in production, a dropped seat. An 18-minute suite that talks to one external host also needs a retry wrapper of its own or it will be flaky regardless of code health.
