Stripe Monetization Briefing

A single session that started as “what are the latest Stripe TODOs?” and ended with a rewritten TODO doc, a verified picture of production, and a three-month plan to actually take money. This page explains everything that was found and decided.

Session date: 2026-08-29 Branch: docs/uni1-refresh Artifact: docs/stripe-todo.md (rewritten, uncommitted)
01

What this session did

The ask was to surface the latest Stripe TODOs and update or create a doc. The existing docs/stripe-todo.md was found but was stale — last touched 2026-08-17 — so rather than trust it, the session verified the current state against live production and the code that reads each setting.

Three pieces of work came out of it:

  1. Rewrote docs/stripe-todo.md against verified state, with production’s own health endpoint as the authority on what’s broken.
  2. Found a monetization risk in the code — the pricing page advertises features that have no enforcement behind them.
  3. Added a 3-month monetization roadmap to the same doc, grounded in what is actually built today.

Nothing was committed. The file is written but unstaged, on a branch that already carries other untracked docs.

03

Finding A — the advertised plan can’t take money

Live revenue-path bug

The annual plan is sold, and its button errors

app/pricing/page.tsx renders a “Best value — save 34%” badge at $79/yr with a working “Start 7-day free trial” button. Clicking it hits app/api/stripe/checkout/route.ts, which finds PRICES.annual empty and returns a CONFIG_ERROR.

So a user who picks the more valuable plan gets an error. That’s a live revenue bug, not just an unset variable — and it’s the item production actively reports.

The price isn’t a free choice either. $79 is already published. 34% off 12 × $9.99 ($119.88) is $79.12, which the page rounds to $79. Creating any other amount makes the marketing copy wrong — and Stripe price objects are immutable once created, so a wrong amount means archive and recreate. The fix belongs in Vercel env (prod + preview), not just .env.local, because it’s a production breakage.

04

Finding B — features are sold that have no gate

Chargeback / consumer-protection risk

The pricing page promises six differentiated features; the code gates on two

FEATURE_TIER_MAP in lib/subscription.ts declares ten features. Grepping every hasEntitlement() call site in the app shows only two are ever actually checked.

Declared feature Times gated in app code Sold on /pricing as
nu_ai9“Nu AI assistant”
signals_digest1“Daily signal digest”
watchlist_alerts0“Watchlist alerts”
morning_briefing0“Morning briefing”
portfolio_suggestions0“Optimizer suggestions”
pro_signals0“Priority signal delivery” (annual)
advanced_ai0“Extended AI context” (annual)
faster_data0—

The pro surfaces that do exist — portfolio, holdfold, council, brief — all gate on nu_ai, not on their own named entitlement. So “Watchlist alerts” and “Morning briefing” are line items on the pricing page with no gate and, in the alerts case, no evident feature at all.

Recommended fix: cut the pricing copy to what ships. hasEntitlement() is a one-line-per-feature map, and the honest short-term move is to reduce the copy — not rush-build four features. Reduce the monthly card to the four things that demonstrably work (signal digest, Nu AI, portfolio health, holdfold/council). For annual, either implement “priority delivery” / “extended context” as real gates, or sell annual purely on price — $79 vs $119.88 is already reason enough.

05

The 3-month monetization roadmap

Grounded in what the code does as of 2026-08-28. The sequence is deliberate: correctness first, measurement second, growth last. Driving traffic into a broken or unmeasured funnel wastes the spend and teaches nothing.

Month 01

Make the funnel actually work

Goal: a user can pay you, and gets exactly what was advertised. No growth spend. The constraint is correctness, not volume.

#TaskWhy it’s here
1.1Create the $79 annual Stripe price, set in VercelThe advertised plan 500s
1.2Swap Clerk to production keysPossibly funnel-fatal, never isolated
1.3Confirm / repair STRIPE_WEBHOOK_SECRETIf placeholder, no subscription ever syncs — a paying user still sees free
1.4Reconcile pricing copy with shipped gatesFinding B — stop advertising ungated features
1.5End-to-end paid smoke test in Stripe test modeNothing above proves the whole chain

1.3 deserves emphasis. Items 1.1 and 1.2 are visible failures. A placeholder webhook secret is an invisible one: checkout succeeds, Stripe charges the card, and the route rejects every event — so the user’s tier never leaves free. They pay and get nothing. Verify this before any real card touches the system.

Exit criterion — one real card, your own, completes a monthly and an annual subscription, unlocks pro, and appears correctly in /dashboard/billing.
Month 02

Learn why people don’t convert

Goal: instrument the funnel, then fix the largest measured drop-off. A grep found no analytics integration anywhere — optimizing without it is guessing.

#TaskNotes
2.1Add one privacy-respecting analytics toolPlausible or PostHog. Update privacy-policy/page.tsx to match, before you add it
2.2Instrument five funnel eventspricing_viewed → checkout_clicked → checkout_completed → trial_started → trial_converted
2.3Add webhook idempotency guardReal volume makes duplicate delivery a real risk
2.4Instrument trial-expiry behaviorisTrialExpired() exists; nothing appears to act on it
2.5Dunning for past_dueThose users keep pro during Smart Retries — correct, but only if someone tells them the card failed
2.6Ship one real annual differentiator or finish the copy cutCloses Finding B properly

Where the leverage probably is. The 7-day trial collects payment upfront, so the classic drop-off is at the card form, not at cancellation. 2.2 will tell you whether that’s true here. Don’t pre-optimize it.

Exit criterion — you can state your pricing-view → paid conversion rate as a number, and you know which single step loses the most people.
Month 03

Grow the top of the funnel, carefully

Goal: more qualified traffic into a funnel you now know converts. Last on purpose.

#TaskNotes
3.1Act on Month 2’s biggest drop-offThe one change with measured justification
3.2Consider trial-without-card as an A/BOnly if 2.2 showed card-form drop-off. Raises starts, lowers conversion-per-start — measure both
3.3Free-tier value loopsignals and portfolio_score are already free. Make the free experience worth returning to weekly
3.4Mobile parity for checkoutMobile calls the portal’s /api/stripe/checkout directly — confirm annual works there once 1.1 lands
3.5Annual upsell to existing monthly subs/dashboard/billing already renders “Switch to annual — save 34%”. Dead until 1.1
3.6Revisit priceOnly with ≥1 month of clean conversion data. $9.99 is an assumption

3.5 is the highest-ROI item in the whole roadmap and costs nothing to build — the button exists. Converting a monthly subscriber to annual takes $119.88/yr of churn-exposed revenue to $79 of committed revenue, trading ~34% of headline rate for a 12× longer commitment and near-zero incremental CAC.

What the roadmap deliberately excludes

  • New pricing tiers. TIER_RANK is {free: 0, pro: 1}. A third tier touches every gate. Not before you can measure the two you have.
  • Usage-based billing for AI. Nu AI calls cost real money per request and flat $9.99 carries margin risk from heavy users — but there’s no usage data yet. Measure in Month 2, decide after Month 3.
  • Building the four ungated features. Cutting the copy is hours; building alerts + briefing + priority delivery + extended context is a quarter on its own, and would delay taking any money at all.

Honest risks

  • Month 1 depends on dashboard access, not code. 1.1–1.3 are all Stripe and Clerk console work. If access is a bottleneck, the plan slips.
  • The Clerk dev-key question is still unresolved. If it was blocking signups, historical conversion data is meaningless as a baseline, and Month 2 starts from zero.
  • No revenue figures appear anywhere because there are none. Every target is a mechanism to fix or a rate to measure. Set numbers after Month 2 produces a baseline.
