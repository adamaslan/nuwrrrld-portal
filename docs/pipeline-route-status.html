P1

afternoon-pipeline has no routes to call

open since 2026-08-14 · PR #59

The workflow shipped its orchestration and failure-notification path ahead of the four routes it calls. All four are still absent from the repo and 404 in production.

  • POST /api/pipeline/signals-refresh
  • POST /api/pipeline/theses-score
  • POST /api/pipeline/council-run
  • POST /api/pipeline/council-validate-distribution

Every scheduled run that clears the market-hours gate fails at the first curl. The last such run (#32891544974, 2026-08-25) failed earlier still, at the secret-preflight step — see the CRON_SECRET issue below. Every run since has gate-skipped, so the 404 hasn't been reached again.

Fix: land the 4 handlers — tracked as its own larger unit of work in the zo-migration status doc; precompute-ai and hydrate-universe are the working template. Until then: gh workflow disable afternoon-pipeline.yml to stop the noise, or leave it enabled as a visible reminder. council-validate-distribution also has no dry_run contract — local-trigger.mjs now refuses to send it without --no-dry-run --yes.
P1

CRON_SECRET unprovisioned everywhere

blocks issue above + all local testing

Missing as a GitHub Actions repo secret (fails the preflight in every scheduled workflow) and missing from .env.local — only PORTAL_PUSH_SECRET is present there, and it is a distinct, non-interchangeable secret. It exists only as a placeholder name in .env.example.

Fix: openssl rand -hex 32 once; set the same value in .env.local, Vercel project env, and gh secret set CRON_SECRET. Must match what every caller sends — GHA workflows and the GCP Cloud Scheduler jobs from setup-schedulers.sh alike.
P2

followed-tickers* routes 503 before auth

new finding

followed-tickers, -select, and -judge are deployed and don't 404 — but return HTTP 503 to an unauthenticated request, ahead of the 401 the auth layer should give. The two sibling routes that behave correctly (precompute-ai, hydrate-universe → 401) confirm the auth middleware itself is fine; something inside these three handlers throws first.

Next step: read the three route.ts files and one request's Vercel runtime log. Likely candidates: a SIGNALS_ENGINE_URL/MCP_BACKEND_URL health check, a missing table, or an explicit "cohort not selected yet" 503 — the monthly job that freezes the cohort has also never completed.
P3

pipeline-failure label missing

Every scheduled workflow's notify job does gh issue create --label pipeline-failure. The label doesn't exist in the repo, so the notify job errors on top of whatever it was reporting.

could not add label: 'pipeline-failure' not found
Fix: gh label create pipeline-failure --color B60205 --description "Scheduled pipeline run failed" — one command. Until then a failure produces two red jobs and no issue.
