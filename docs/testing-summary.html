Why CI stayed red: five stacked failures

Each fix revealed the next, and the error message pointed at the wrong layer almost every time. Recorded in full as incident-2026-08-17-e2e-ci-cascade.

  1. Wrong Clerk instance.env.local held two key pairs; dotenv is last-wins, so the production pair was active and got synced to CI. Symptom: “Publishable key not valid.”
  2. Test user in the wrong instanceCreated in production, not dev. Valid credentials, rejected sign-in.
  3. Concurrency cancellationA docs commit landing seconds later triggered cancel-in-progress. Symptom: cancelled — indistinguishable from a manual cancel.
  4. Job timeout set by guesstimeout-minutes: 5, but installing browsers alone took 2m48s. Also reported as cancelled, which is what made this and #3 cost two cycles.
  5. A one-character secretThe actual root cause of the original symptom — see below.
Root cause worth remembering beyond this repo 
printf '%s' "$value" | gh secret set "$name" --body -   # WRONG
printf '%s' "$value" | gh secret set "$name"            # correct

gh secret set --body takes the value as a literal string. It reads stdin only when --body is omitted. So every synced secret was stored as the single character -, and gh reported success. A Clerk key verified valid against Clerk's own API still failed in CI, because the value in CI was one byte. Proven with a throwaway workflow echoing ${#PK}: 1 before, 58 after. Crucially, gh secret list cannot detect this — it proves a name exists, never that the value is intact.
