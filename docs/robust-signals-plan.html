nuwrrrld-portal · signal architecture · 2026-08-18

You already built the robust signal engine. It just isn't plugged in.

The portal computes four indicators. signals-app computes roughly fifty per bar across nineteen detectors, with confluence scoring, multi-timeframe composites, a historical backtest engine, and confidence calibration — and it exposes exactly the HTTP contract lib/backtest.ts was written to consume. The gap is one environment variable and a deploy, not a rewrite.

Direct answer, corrected

The portal's signals are not your most robust. signals-app is.

My first pass read only the markdown inventory in homebase and concluded the portal was fifth-deepest with no better option available. Checking boll4-500b.md and boll4-500c.md — and then the code they point at — changes the conclusion materially.

~/code/signals-app is a 5,677-line modular Python engine with 19 detector classes, per-detector timeout isolation, parameter grids, pivot caching, divergence detection, data-quality scoring, a bar-by-bar historical scanner, a backtest hit-rate engine, and a calibration module that feeds measured hit rates back into confidence labels.

And critically: its GET /backtest/{symbol}?period=2y route returns by_category / by_strength buckets — the exact shape lib/backtest.ts validates. The portal was built to talk to this service. SIGNALS_ENGINE_URL is empty, so it never has.

The plan

Reordered around the finding: connect what exists before building anything new. Every phase is independently shippable.

Phase 0

Deploy signals-app and set one variable

highest value per hour of work

Nothing else in this plan comes close on effort-to-payoff. The engine is written, tested, and contract-compatible. Deploying it lights up the track-record badge across the entire UI and gives every later phase a measurement substrate.

  • Deploy signals-app — Cloud Run or Modal; it is a FastAPI service with a /health route
  • Set SIGNALS_ENGINE_URL in Vercel and .env.local
  • Exit test: fetchBacktest("AAPL") returns non-null; TrackRecordBadge renders real hit rates

Verify the free-tier data source first. signals-app fetches via yfinance, which is unmetered but unofficial and rate-limits under load. Fine for on-demand per-symbol backtests; not a substitute for the Alpaca lane on a 518-symbol nightly sweep.

Phase 1

Universe cards at current depth

unblocks four dark features

Coverage before depth. Four indicators across 518 tickers is worth far more than fifty across zero, and it produces the row corpus later phases measure against. Alpaca credentials are live and verified this session.

  • Seed ticker_universe — 518 tickers, dry-run verified
  • Hydrate locally over the full list, then deploy the Modal cron
  • Exit test: ≥1,000 card rows (518 × 2 horizons), coverage ≥95%
Phase 2

Depth — port the detector set, don't rewrite it

4 → ~50 signals/bar

My first draft proposed hand-porting 20 indicators into the Modal app. That would have been a sixth independent implementation of RSI across your projects. The corrected approach: make signals-app the sole owner of indicator math and have the hydration lane call it.

Modal cron (nightly) ├─ GET /api/pipeline/hydrate-universe → 518 symbols ├─ signals-app POST /signals/batch → confluence + MTF per symbol │ (19 detectors, timeout-isolated, calibrated confidence) ├─ map ConfluenceResult → StateKeyParts → TAXONOMY_V2 └─ POST /api/pipeline/hydrate-universe → ticker_cards
  • New work is an adapter, not an engine — map signals-app's confluence output onto the portal's taxonomy buckets
  • signals-app needs a batch endpoint; today /signals is per-symbol
  • Taxonomy grows from 6 dimensions to 8 via family-level composite buckets (momentum: weak/mixed/strong), never one dimension per indicator
  • Retire the Modal app's inline indicator math once the adapter is proven — do not leave two implementations live

Combinatorics guard. Six buckets already yield 486 states. Family-level composites keep TAXONOMY_V2 enumerable so the grounding-pack join stays a plain indexed lookup rather than a search.

Phase 3

Calibrated hit rates keyed on taxonomy state

makes signal quality falsifiable

signals-app already computes hit rates by category and by strength. The portal's addition is keying them on state_key, so a live card joins directly to its own historical record.

  • Extend backtest_hit_rates with a state_key column
  • Backfill 5 years × 518 symbols on Modal — bounded CPU, no model calls
  • Reuse calibration.py's CALIBRATION_MIN_BUCKET_SIZE rule — a hit rate from 4 samples is noise, not a probability
  • Exit test: every occupied state carries n ≥ 100 or is explicitly flagged low-confidence

Look-ahead bias is the defining risk. Indicators must be recomputed on a [0:t] slice per bar, never sliced from a whole-series result. detection/historical.py already scans bar-by-bar — confirm it recomputes rather than slices before trusting any number it produces. This is how a backtest reports 87% and delivers 51%.

Phase 4

Automated AI signal research

credible only after Phase 3

With a labeled corpus, the model stops narrating signals and starts interrogating them. Worthless before Phase 3 — an LLM hypothesizing over unmeasured signals is generating plausible sentences, not research.

weekly cron ├─ SELECT state_key, hit_rate, n FROM backtest_hit_rates → the evidence ├─ model proposes 10 hypotheses (~2 batched calls) → cheap ├─ each → parameterized SQL → measured, not asserted → 0 model calls └─ survivors → taxonomy proposal → HUMAN REVIEW → V3
  • The model never scores itself — every hypothesis becomes a SQL query the database answers
  • Survivors clearing a significance floor become candidate composite buckets
  • Weekly digest: what was tested, what survived, what died, with sample counts

The human gate is not optional. A loop that promotes its own hypotheses into the taxonomy and then measures against the taxonomy it just changed will overfit to noise and report improvement while doing it. Promotion is a reviewed PR, always.

Five independent RSI implementations exist across your projects. That is the real robustness risk — more than any single engine's depth.

When two engines disagree on AAPL's RSI — different lookback convention, different close series, both defensible — the portal serves whichever wrote last, and the symptom is "the numbers flicker" long before anyone diagnoses it. Pick one home for the math and write down which.

Risks

  • yfinance dependency in signals-app — unofficial and rate-limited; fine on-demand, wrong for a 518-symbol sweep. Keep Alpaca for breadth
  • Look-ahead bias — verify historical.py recomputes per slice rather than slicing a whole-series result
  • Taxonomy explosion — family-level composites must be enforced in review, not merely intended
  • Two engines during Phase 2 — the Modal app's inline math and signals-app both live; retire one on a deadline
  • Blocker 1 persists — ETF cards fill 1 of 5 taxonomy inputs and stay unexplainable; depth widens that gap rather than closing it
  • Overfitting in Phase 4 — the human promotion gate is the only real defense
