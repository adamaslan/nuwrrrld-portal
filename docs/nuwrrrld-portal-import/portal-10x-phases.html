NuWrrrld Portal · Roadmap

10x the Council, the DB, & the UI

Five workstreams turning the portal from a thin display layer into a persistent, grounded, neon-dark product. Ordered by dependency — but two tracks run in parallel. Full detail lives in portal-10x-council-db-local.md.

⚠ Reality check: signals-app and the portal are not connected

The portal has zero client for signals-app — every data path points at the gcp3 Cloud Run backend (MCP_BACKEND_URL). And signals-app's API isn't deployed anywhere: no Dockerfile, no host — its FastAPI service only runs on localhost:8000 with no auth and allow_origins=["*"].

So wiring them together is real work — it's Workstream 0, and the council's backtest grounding depends on it. Until then, the council grounds on gcp3's data (already reachable), just not signals-app's hit-rates.

The phases

  1. Phase 1

    Database first

    Size: S–M

    Neon is already provisioned — this is schema + migration, not infra. Add the council/verdict/hit-rate tables and move the in-memory cache Maps (which reset on every serverless cold start) into Postgres.

    Unblocks: the #1 launch blocker (data loss), council persistence, the backtest hit-rate table.

  2. Phase 2

    Backend runs locally

    Size: S

    Add a CACHE_BACKEND=sqlite switch so gcp3's FastAPI service runs without Firestore/GCP, plus a uvicorn entry point. Point the portal at localhost and iterate offline.

    Unblocks: cheap, GCP-free iteration on every later phase.

  3. Phase 3

    Connect signals-app → portal

    Size: M

    The missing wire. Recommended path: a nightly calibrate.py job writes backtest hit-rates into Neon (backtest_hit_rates), so the council reads Postgres it already talks to. Deploy + secure the live API only if the on-demand drill-down is needed.

    Unblocks: the council's backtest-grounded confidence.

  4. Phase 4

    Council debate protocol

    Size: M–L

    The actual 10x. Grow from 2 single-shot seats to 6 roles (adds Risk, Macro, Quant, Chair), a 2-round parallel debate + Chair synthesis into a structured verdict, grounded on real data — not prompt strings.

    Unblocks: persistent, auditable, multi-seat deliberation.

  5. Phase 5

    Memory & track record

    Size: M

    Per-user and per-ticker memory, plus a /dashboard/council page scoring past verdicts against realized outcomes — "HIGH-confidence calls: 64% hit rate, n=41." The council confronting its own record is the biggest trust win.

    Unblocks: the product/trust payoff.

  6. Phase 6

    Cost control

    Size: S

    Free-tier-only models, per-user daily deliberation quotas in Neon, and a by-(ticker, day) deliberation cache so the second user asking about AAPL gets the saved session, not 11 fresh model calls.

    Unblocks: safe wider rollout.

  7. Parallel

    Neon dark-mode frontend

    Size: S–M

    Always-dark near-black canvas with blue/red neon flares (this very page is the look). Ambient blurred radial glows behind content, restrained accent-glow on emphasis only — and WCAG AA throughout: body text never neon, direction never hue-alone, motion respects prefers-reduced-motion.

    Unblocks: the signature look — independent, hand to a parallel track.

Dependencies: Phases 1 & 2 are independent and parallel. Phase 3 needs Phase 1's hit-rate table for the push path. Phase 4 can start on gcp3-only grounding before Phase 3 lands, then gains backtest hit-rates once it ships. The neon frontend is fully independent of the rest.
