1 · Current State & the Gap

What exists today, and the interactivity it does not yet cover.

✅ What's in place

  • vitest v4 with test and test:integration scripts
  • 8 logic suites in __tests__/ (council verdict/critique/validate, signal-queue, live-price, grounding, public-demo)
  • @ path alias resolved in vitest.config.ts

⚠️ The gap

  • environment: "node" — no DOM, so no component can be rendered or clicked
  • No Testing Library, no user-event, no jsdom
  • No E2E runner (Playwright/Cypress)
  • Zero coverage of clicks, fetches, animations, focus, or clipboard — all the interactivity
Strategy in one line: keep the fast node logic tests, add a jsdom component layer for interactivity, and cap it with a thin Playwright E2E layer for the flows that only break in a real browser (animation, scroll, streaming, clipboard permissions).

4 · Core Features — Robust Coverage

The four interactive pillars of the product. Each gets its own contract: inputs, states, and the exact assertions that lock it down.

4.1 · AI Chat (NuAIChat & SignalAskAnything)

The highest-value, most stateful surface. A single component juggles input, network, streaming/loading, auto-scroll, errors, and a rate-limit ceiling.

States to prove

  • idle → empty, send disabled on blank input
  • loading → send disabled, spinner/optimistic message
  • success → answer appended, input cleared, scrolled to bottom
  • error → error text shown, input preserved
  • limitReached → composer locked, upgrade CTA

How it's tested

  • Comp mock fetch, type + click, assert DOM per state
  • Prompt-chip click sends the chip text
  • Auto-scroll: assert scrollIntoView called on the ref
  • E2E one real round-trip against a stubbed /api/nuai

4.2 · HoldFold Verdict Explorer

Search + filter + modal + two independent async actions (add-to-watchlist, ask-council). The richest client state machine in the app.

  • Search — typing filters the visible verdict list (case-insensitive, ticker + name).
  • Filter tabs — all / HOLD EM / FOLD EM / NEUTRAL narrow results; combined with search.
  • Modal — selecting a verdict opens it; ✕ / Esc / backdrop closes it; focus trapped inside.
  • Async actions — each has its own idle/loading/done/error lifecycle mocked independently.

4.3 · Share (SignalShareButton)

Small but permission-sensitive. Clipboard is mocked at component layer and exercised for real (with granted permission) at E2E.

  • Click → navigator.clipboard.writeText called with the canonical URL.
  • Label flips to "Copied!" then reverts after the timeout (fake timers).
  • Rejected clipboard promise → graceful fallback, no crash.

4.4 · Scroll-Driven Motion (CouncilScrollDebate, Parallax, Reveal, StatCounter)

Animation correctness is split: logic (which step for a given scroll progress) is unit-testable; pixels (does the layer actually move) is visual/E2E.

  • Pure step-mapping function tested at unit layer (progress → step index).
  • StatCounter reaches its final value; short-circuits to the value under reduced-motion.
  • Observers/rAF are cleaned up on unmount (no leaks) — asserted at component layer.

6 · How Each Test Actually Works

Concrete mechanics per layer — the wiring, the fakes, and a representative example for each.

6.1 · Split the Vitest project into two environments

Keep node-fast logic tests and add a jsdom project for components — one config, two workspaces, so npm test runs both.

// vitest.config.ts — replace single config with projects
import { defineConfig } from "vitest/config";
export default defineConfig({
  test: {
    projects: [
      { // fast pure logic — unchanged
        test: { name: "unit", environment: "node",
                include: ["__tests__/**/*.test.ts"] } },
      { // NEW: interactivity
        test: { name: "components", environment: "jsdom",
                setupFiles: ["./test/setup.ts"],
                include: ["components/**/*.test.tsx", "app/**/*.test.tsx"] } },
    ],
  },
});

Add dev deps: @testing-library/react · @testing-library/user-event · @testing-library/jest-dom · jsdom · jest-axe

6.2 · The jsdom setup file — fake what jsdom lacks

jsdom has no IntersectionObserver, matchMedia, scrollIntoView, or clipboard. The setup file polyfills them so animation/observer components mount without throwing.

// test/setup.ts
import "@testing-library/jest-dom/vitest";
import { vi, afterEach } from "vitest";
import { cleanup } from "@testing-library/react";

afterEach(cleanup);

// prefers-reduced-motion drives StatCounter / MagneticCTA branches
globalThis.matchMedia ??= (q) => ({
  matches: false, media: q, onchange: null,
  addEventListener: vi.fn(), removeEventListener: vi.fn(), dispatchEvent: vi.fn(),
});

class IO { observe = vi.fn(); unobserve = vi.fn(); disconnect = vi.fn(); }
globalThis.IntersectionObserver = IO as any;
Element.prototype.scrollIntoView = vi.fn();

6.3 · Component test — SignalAskAnything (fetch + states)

The workhorse pattern: render, mock the network, drive it with userEvent exactly as a human would, assert the resulting DOM. No implementation details — only what the user sees.

// components/SignalAskAnything.test.tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { vi, expect, test, beforeEach } from "vitest";
import SignalAskAnything from "./SignalAskAnything";

beforeEach(() => { globalThis.fetch = vi.fn(); });

test("asks a question and renders the answer", async () => {
  (fetch as any).mockResolvedValue({
    ok: true, json: async () => ({ answer: "NVDA looks strong." }),
  });
  const user = userEvent.setup();
  render(<SignalAskAnything ticker="NVDA" />);

  await user.type(screen.getByRole("textbox"), "Is it a buy?");
  await user.click(screen.getByRole("button", { name: /ask/i }));

  expect(await screen.findByText(/looks strong/i)).toBeInTheDocument();
  expect(fetch).toHaveBeenCalledWith(
    "/api/signals/NVDA/chat", expect.objectContaining({ method: "POST" }));
});

test("shows an error and keeps the question on failure", async () => {
  (fetch as any).mockResolvedValue({ ok: false, status: 500 });
  const user = userEvent.setup();
  render(<SignalAskAnything ticker="NVDA" />);
  await user.type(screen.getByRole("textbox"), "why?");
  await user.click(screen.getByRole("button", { name: /ask/i }));
  expect(await screen.findByRole("alert")).toBeInTheDocument();
  expect(screen.getByRole("textbox")).toHaveValue("why?"); // preserved
});
Why role queries, not data-testid: querying by role/label tests the accessibility tree — the same thing assistive tech uses. A test that can't find the button by its accessible name is telling you a real a11y bug, for free.

6.4 · Timers & animation — StatCounter and the "Copied!" revert

rAF and setTimeout are made deterministic with fake timers, so a count-up that takes 1.2s of wall-clock runs in microseconds and asserts its end state.

vi.useFakeTimers();
render(<StatCounter value={1200} durationMs={1200} inView />);
await vi.runAllTimersAsync();          // flush rAF ticks
expect(screen.getByText("1,200")).toBeInTheDocument();
vi.useRealTimers();

// reduced-motion → jumps straight to value, no animation frames
matchMedia.mockReturnValueOnce({ matches: true } as any);
render(<StatCounter value={99} inView />);
expect(screen.getByText("99")).toBeInTheDocument();

6.5 · Scroll logic — extract the pure part first

Don't test scroll math through the DOM. Refactor the progress→step mapping in CouncilScrollDebate into a pure exported function and unit-test it; leave "does it actually advance while scrolling" to E2E.

// pure, node-testable
expect(stepForProgress(0.00, 4)).toBe(0);
expect(stepForProgress(0.50, 4)).toBe(2);
expect(stepForProgress(0.99, 4)).toBe(3);   // clamps, never overflows

6.6 · E2E — NuAIChat round-trip with a stubbed API

Playwright drives real Chromium. Network is intercepted so tests are deterministic and don't spend model tokens; everything else (scroll, focus, streaming render) is real.

// e2e/nuai.spec.ts
import { test, expect } from "@playwright/test";

test("chat sends and renders a grounded answer", async ({ page }) => {
  await page.route("**/api/nuai", (r) =>
    r.fulfill({ json: { answer: "AAPL is HOLD EM." } }));

  await page.goto("/dashboard/nuai");
  await page.getByRole("textbox").fill("What about AAPL?");
  await page.getByRole("button", { name: "↑" }).click();
  await expect(page.getByText("AAPL is HOLD EM.")).toBeVisible();
});
Auth in E2E: Clerk-gated routes use a seeded test session (storage state saved once via a global setup, reused across specs) so you never log in per test.

6.7 · Clipboard — mock at unit, real at E2E

// component layer
const writeText = vi.fn().mockResolvedValue(undefined);
Object.assign(navigator, { clipboard: { writeText } });
await user.click(screen.getByRole("button", { name: /share/i }));
expect(writeText).toHaveBeenCalledWith(expect.stringContaining("/verdict/"));
expect(await screen.findByText(/copied/i)).toBeInTheDocument();

E2E grants clipboard-read/write permission in the browser context to exercise the real API.

7 · Accessibility & Motion — Woven In, Not Bolted On

Interactivity that isn't operable by keyboard or screen reader isn't done. These checks run inside the layers above.

Automated axe pass

Every component test ends with expect(await axe(container)).toHaveNoViolations(). Catches missing labels, bad contrast, invalid ARIA — the things role-queries alone miss.

Keyboard operability

Drive with user.keyboard(): Tab reaches every control, Enter/Space activate, Esc closes modals, focus order is logical, focus returns to the trigger on close.

Reduced motion

With matchMedia matches:true, assert Magnetic/Parallax apply no transform and StatCounter snaps to its value — honoring the useReducedMotion branches already in the code.

Live regions

Chat answers and error toasts live in aria-live / role="alert" regions so screen readers announce async results. Tests assert the role, not just the text.

9 · CI & Tooling

Fast feedback locally, full gate on PRs.

1
Pre-commit / watch — vitest --project unit --project components run on changed files. Sub-second for logic, fast for jsdom.
2
PR gate — all vitest projects + Playwright E2E headless + jest-axe. Blocks merge on any failure.
3
Nightly / pre-release — visual snapshots (Playwright/Storybook) + Lighthouse CI budgets on key routes.
4
Coverage — vitest --coverage with a floor on components/ and app/**/*Client.tsx; report, don't chase 100%.

11 · Admin Dashboard (nulogdash)

The one real admin surface in the app — app/dashboard/nulogdash/page.tsx — plus the gate it depends on, lib/nulogdash.ts. This section is scoped to the actual component, not the static HTML prototypes in docs/nulogdash-admin.html/nulogdash-admin-site.html, which model a richer client-side console (modals, mutating buttons) that doesn't exist in code yet.

Shape of the real page: an async server component, not a client island. It reads .nulogdash/latest.json off disk (force-dynamic, no caching) and renders read-only tables. The only client-side interactivity in the shipped DOM is the native <details>/<summary> reason disclosure per row — everything else is server-rendered HTML.

11.2 · Unit tests — the admin gate (highest priority; this is an authz boundary)

These are pure functions today (AdminIdentity is a structural interface specifically so the gate is unit-testable without constructing a real Clerk User) — no DOM, no server, node environment is enough.

// lib/nulogdash.test.ts
import { expect, test } from "vitest";
import { isNulogdashAdmin, canPerformAdminAction } from "./nulogdash";

const identity = (overrides: Partial<Parameters<typeof isNulogdashAdmin>[0]> = {}) => ({
  primaryEmailAddressId: "id1",
  emailAddresses: [{ id: "id1", emailAddress: "admin@nuwrrrld.com",
                     verification: { status: "verified" } }],
  ...overrides,
});

test("denies everyone when allowlist is unset", () => {
  delete process.env.NULOGDASH_ADMIN_EMAILS;
  expect(isNulogdashAdmin(identity())).toBe(false);
});

test("allows a verified primary email on the allowlist", () => {
  process.env.NULOGDASH_ADMIN_EMAILS = "admin@nuwrrrld.com";
  expect(isNulogdashAdmin(identity())).toBe(true);
});

test("rejects a non-primary address even if it's on the allowlist", () => {
  process.env.NULOGDASH_ADMIN_EMAILS = "other@nuwrrrld.com";
  expect(isNulogdashAdmin(identity({
    emailAddresses: [
      { id: "id1", emailAddress: "admin@nuwrrrld.com", verification: { status: "verified" } },
      { id: "id2", emailAddress: "other@nuwrrrld.com", verification: { status: "verified" } },
    ],
  }))).toBe(false);
});

test("rejects an unverified primary email", () => {
  process.env.NULOGDASH_ADMIN_EMAILS = "admin@nuwrrrld.com";
  expect(isNulogdashAdmin(identity({
    emailAddresses: [{ id: "id1", emailAddress: "admin@nuwrrrld.com",
                       verification: { status: "unverified" } }],
  }))).toBe(false);
});

test("canPerformAdminAction requires admin AND twoFactorEnabled", () => {
  process.env.NULOGDASH_ADMIN_EMAILS = "admin@nuwrrrld.com";
  expect(canPerformAdminAction(identity({ twoFactorEnabled: false }))).toBe(false);
  expect(canPerformAdminAction(identity({ twoFactorEnabled: true }))).toBe(true);
});
Why this table outranks everything else in §11: a bug here doesn't degrade a feature, it leaks an internal test-sweep report (or worse, once mutating actions land) to the wrong person. Treat lib/nulogdash.test.ts as a required file, not a nice-to-have — a PR that touches isNulogdashAdmin or canPerformAdminAction without updating this suite should be blocked in review.

11.3 · Component tests — rendering logic without a real Clerk session

The page itself is an async server component (can't render() it directly with Testing Library today). Two practical options, in order of preference:

  1. Extract the pure pieces. Pull the counts reducer (page.tsx:90-95) and the not-run/exercised split (page.tsx:97-98) into named exports in lib/nulogdash.ts and unit-test them directly against a fixture NulogdashRun — cheaper and more precise than asserting through rendered HTML.
  2. Component-test the presentational children (StatusBadge, FeatureRow, MfaNotice) in isolation with jsdom + Testing Library — these are plain functions returning JSX, no async/server dependency, so they render normally.
// components-ish unit test against extracted pure logic
import { splitResults, summarizeCounts } from "@/lib/nulogdash";
const results = [
  fixture({ status: "pass" }), fixture({ status: "fail" }),
  fixture({ status: "blocked" }), fixture({ status: "not_run" }),
];
expect(summarizeCounts(results)).toEqual({ pass: 1, fail: 1, blocked: 1, not_run: 1 });
const { notExercised, exercised } = splitResults(results);
expect(notExercised).toHaveLength(2);
expect(exercised).toHaveLength(2);

11.4 · E2E — the only layer that can prove the auth/authz gate end-to-end

Three seeded Clerk sessions cover every branch: signed-out, signed-in-non-admin, signed-in-admin (with and without MFA). This is the layer that actually exercises redirect() and notFound() as Next.js middleware + routing would in production.

// e2e/nulogdash-admin.spec.ts
import { test, expect } from "@playwright/test";

test("signed-out visitor is redirected to sign-in", async ({ page }) => {
  await page.goto("/dashboard/nulogdash");
  await expect(page).toHaveURL(/\/sign-in\?redirect_url=/);
});

test.describe("signed in, not on the allowlist", () => {
  test.use({ storageState: "e2e/.auth/non-admin.json" });
  test("gets a 404, not a redirect to the console", async ({ page }) => {
    const res = await page.goto("/dashboard/nulogdash");
    expect(res?.status()).toBe(404);
  });
});

test.describe("admin without MFA", () => {
  test.use({ storageState: "e2e/.auth/admin-no-mfa.json" });
  test("sees the report and the MFA notice, no mutating buttons", async ({ page }) => {
    await page.goto("/dashboard/nulogdash");
    await expect(page.getByText(/two-factor authentication required/i)).toBeVisible();
    await expect(page.getByRole("heading", { name: "nulogdash" })).toBeVisible();
  });
});
Seed fixtures once: a global-setup script creates the three Clerk test users (non-admin, admin-no-mfa, admin-with-mfa) and saves each storage state to e2e/.auth/*.json, reused across every spec — same pattern as §6.6's chat E2E.

11.5 · Prototype HTML files — not the app, treat as design reference only

docs/nulogdash-admin.html + nulogdash-admin.css are a static mockup of a future, richer console (Refresh, Create User, Impersonate/Disable/Reset PW, Reindex/Backup/Deploy with native confirm() guards, a focus-trapped modal). None of this exists in page.tsx yet — the real page has no mutating buttons at all, only the MFA-gated promise of them. If/when those actions get built for real:

  • Every mutating action must call canPerformAdminAction() server-side — never trust a disabled client button alone, since that's trivially bypassed.
  • The prototype's native window.confirm() pattern won't survive the port to React — re-home those as an accessible modal (focus trap, Esc-to-close, focus-return-on-close) and give it the same component-test treatment as §5's "Modal focus trap" row.
  • Destructive actions (deployBtn in the mockup) need an E2E test asserting the confirmation step cannot be skipped — mirrors this repo's own non-negotiable "warn before destroying state" rule.
