What it is

A financial signal detection and LLM-synthesis app for equities, built for a single local user doing semi-automated technical analysis — explicitly not a multi-tenant SaaS.

Give it a ticker and a period. It runs 19 independent technical-analysis detectors over OHLCV bars, aggregates them into a weighted confluence score, and optionally asks an LLM to turn that into a structured directional call with confidence and cited evidence.

The defining architectural choice is separation into replaceable layers: indicators, detection, scoring, and synthesis are distinct packages with typed boundaries. Every prior signal project on this machine was a monolith — boll-4-april-500.py was one ~1,700-line class where an exception in the Ichimoku detector aborted every other category's results.

The pipeline

Five layers, each independently testable.

GET /signals/{symbol}?period=3mo │ L1 data/fetcher.py yfinance OHLCV → ≥20 bars or HTTP 400 L2 indicators/compute.py parameter grids → RSI×5, MACD×4, BB 4×4, MA×11… indicators/pivots.py O(1) prefix lookup (precomputed pivot cache) indicators/divergence.py price·volume·OBV divergence L3 detection/orchestrator 19 detectors → per-detector TIMEOUT ISOLATION L4 scoring/confluence.py weighted aggregate → score, BUY/SELL/HOLD, confidence scoring/calibration.py measured hit-rates → nudges confidence label L5 synthesis/mtf_llm.py Gemini → structured call + evidence (failure ≠ 500; falls back)
L3

Detection — the robustness layer

19 classes

detect_all_signals() runs each detector in its own thread pool with a timeout. A single detector failing or hanging cannot crash the pipeline — the run degrades and reports .degraded / .warnings on a typed SignalList rather than returning a partial result that looks complete.

The orchestrator's docstring credits the port: "Ported from gcp-app-w-mcp1/mcp-finance1" — this is consolidated prior work, not a greenfield rewrite.

L4

Confluence — gated action, not just a score

two conditions

A BUY requires both a score above threshold and a minimum count of agreeing signals — so one extreme reading can't manufacture a call on its own. 

CONFLUENCE_BUY_THRESHOLD    =  0.35    CONFLUENCE_BUY_MIN_SIGNALS  = 3
CONFLUENCE_SELL_THRESHOLD   = -0.35    CONFLUENCE_SELL_MIN_SIGNALS = 3

Scores normalize to [-1, 1], with a per-category confidence bonus (MA_CROSS / MACD / VOLUME get +0.5; OBV_CMF / ICHIMOKU +0.3).

L4+

Calibration — the rarest piece

closes the loop

derive_strength_hit_rates() converts backtest output into a strength→hit-rate map that rank_signals() consumes to nudge its confidence label toward what actually happened. Buckets below CALIBRATION_MIN_BUCKET_SIZE = 30 are dropped — "a hit-rate from 4 signals is noise, not a calibrated probability."

No other signal project on this machine measures whether its own confidence labels are honest. This one does, and discards the samples too small to trust.

What's exposed vs what exists

The most consequential finding. Substantial capability is built, tested, and unreachable over HTTP.

SignalOutput.matrix is always None in the live route. The multi-timeframe composite — 1D/5D/1M/3M/6M, weighted {0.10, 0.15, 0.25, 0.30, 0.20} with 3M carrying most weight — runs only in tests and CLI.

No batch endpoint. Every route is per-symbol. Any use that walks a 518-ticker universe needs one added, or it makes 518 sequential yfinance-backed calls. This is the single largest blocker to using signals-app as the portal's hydration engine.

The two were built to fit together. Nobody has connected them.

What it does better than everything before it

  • Per-detector timeout isolation — every prior engine was a monolith where one bad detector killed the whole scan
  • Typed degradation — SignalList.degraded / .warnings distinguish "partial" from "complete", so a degraded run can't masquerade as a clean one
  • Gated actions — BUY needs score and agreeing-signal count, not a single extreme reading
  • Measured confidence — calibration feeds real hit rates back into labels, with a minimum sample size
  • Multi-timeframe weighting — short timeframes deliberately down-weighted as noisier
  • LLM failure is non-fatal — synthesis errors fall back and tag unavailable rather than 500-ing
  • Its own wiki — entities, concepts, decisions, ops, with known gaps explicitly flagged for future ingest

It is a consolidation, not a rewrite. The orchestrator is ported from gcp-app-w-mcp1; relative_strength.py is adapted from gcp3's technical_signals.py, decoupled from Firestore so callers control the data source; the parameter grids match boll-4-april-500.py's. This is the accumulated signal work from four projects with an architecture around it.
