NuWrrrld Portal — Storage & DB Structure

How the Next.js web portal persists state: server-side Neon Postgres + client-side browser storage.
Next.js 16 · App Router Neon Postgres (serverless) Clerk auth 13 tables · 1 function generated 2026-07-24
One-paragraph summary. All durable state lives in a single Neon Postgres database, reached through one serverless client (lib/db.ts → DATABASE_URL). The schema (lib/db/schema.sql) is idempotent and applied at build time. Most tables exist because a 2026-07-15 audit replaced in-memory Maps that were silently wiped on every serverless cold start. The only client-side storage is browser localStorage, used for exactly one non-critical UI preference. Auth sessions are held by Clerk, not by app-owned cookies.

1 · The database connection

lib/db.ts singleton

A single Neon HTTP client shared by every server module. There is no ORM and no connection pool object — @neondatabase/serverless issues tagged-template SQL over HTTP, which suits serverless/edge cold starts.

import { neon } from "@neondatabase/serverless"; const sql = neon(process.env.DATABASE_URL!); export default sql;

Migrations

Schema is applied by scripts/db-migrate.mjs, wired two ways in package.json:

  • prebuild → runs automatically before every next build
  • npm run db:migrate → manual, loads .env.local

Every statement is CREATE … IF NOT EXISTS, so re-running is safe.

Identity & tenancy

User-scoped rows key on user_id text = the Clerk userId. There are no users / accounts tables in the portal — Clerk is the system of record for identity and entitlements (publicMetadata.subscription_status).

3 · Client-side / local storage

The portal stores almost nothing in the browser. There is one localStorage touchpoint and no app-owned cookies (cookies() is never called; sessions are Clerk-managed).

lib/shared/prefs.ts → window.localStorage

A tiny cross-platform persistence seam: getPref(key) / setPref(key, value), async-shaped so shared logic doesn't care whether it runs on web (localStorage) or mobile (expo-secure-store). SSR-guarded (typeof window === "undefined") and fully best-effort — a failed read/write returns null / no-ops rather than throwing.

keywritten byvalue

This mirrors gcp3-mobile/lib/shared/prefs.ts (same get/set signature). Because it is non-critical UI state, losing it degrades to "filters reset to default" — never an error.

4 · Design principles the schema encodes

  • No durable state in process memory. Serverless cold starts wipe module-level Maps; the 2026-07-15 audit moved every such Map into Neon. Comments in schema.sql name each Map it replaced.
  • Cache vs. data split. Cache tables (*_cache) degrade silently on read failure; primary data (watchlist_items) surfaces a 503. The distinction is deliberate and enforced in the store modules, not just convention.
  • Clerk owns identity. No user table; everything foreign-keys conceptually to a Clerk user_id text.
  • Grounding is compile-time, not request-time. corpus_chunks + grounding_pack replace live RAG with a pre-compiled, citable lookup — written weekly, read at zero model cost.
  • Idempotent, build-time migration. One schema.sql, applied via prebuild; no migration history table, no down-migrations.
